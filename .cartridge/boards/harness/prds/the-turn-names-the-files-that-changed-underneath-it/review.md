### Findings and concrete revisions

**B1 (blocking) — `resolve_drift`/`describe_drift` read the wrong shape of the `sessions` `drift` reply; a real drift never renders.**
`spec01.md`'s "Ordered steps" §5 (`resolve_drift`, `describe_drift`) calls `describe_drift(&reply["report"])` and then reads `report["changed"]` / `report["gone"]` off that value. The frozen contract this row itself cites as authoritative — `prd.ctg/.cartridge/boards/sessions/prds/file-drift-awareness/specs/spec01.md:236-239` (`sessions_inner`, the `"drift"` arm) — answers `Ok(json!({"id":id, "report":report["report"], "changed":report["changed"], "gone":report["gone"]}))` when something moved: `report`, `changed` and `gone` are three **sibling** top-level keys, and `report` itself holds the **pre-rendered text string** (the sessions spec: "a header line plus one line per path... so the harness injects a string and invents no wording," same file ~line 205), not an object nesting `changed`/`gone`. `reply["report"]` is therefore a JSON string whenever something drifted, never an object with `changed`/`gone` inside it. I verified the consequence by compiling and running the exact indexing: `serde_json::json!("Changed:\n- foo.rs")["changed"]` evaluates to `Value::Null`, whose `.as_array()` is `None` — so `describe_drift`'s `changed`/`gone` are always empty and it always returns `None`, for every real, populated report, not only for a failure or an absent one. This is the harness's own PRD text ("in order to match the sessions op's `report: null` versus `{changed, gone}` contract," `prd.md` Evidence, harness board) misreading the same document the sessions spec calls frozen; the sessions board's own review (round 3, no objection to the contract across 3 rounds) confirms the real shape is the flat one, not the nested one the harness spec assumes. **This is not a hypothetical edge case: it is the only path by which this PRD's entire outcome could ever be observed, and it is broken by construction.** Fix: either use `reply["report"]` directly as the (already-formatted) block body when non-null and drop `describe_drift`'s own formatting entirely, or read `reply["changed"]`/`reply["gone"]` at the top level of `reply`, not nested under `report`.

**B2 (blocking, from task point 3) — the prefix/ordering test cannot catch the one regression it exists to name.**
I copied `harness.ctg` to a throwaway tree (`/tmp/harness-review.*`, `rsync -a --exclude target`, isolated `CARGO_TARGET_DIR`, `env -u CARTRIDGE_YOLO` throughout, cleaned up after), applied every one of the spec's ten "Ordered steps" verbatim, and confirmed `cargo test -p harness --lib` passes 41/41 and `cargo clippy -p harness --all-targets -- -D warnings` is clean. I then built a second copy and applied one deliberate mutation: moved the drift append to run **before** the telemetry append instead of after (still after `record`/`notice`, i.e. exactly "above another tail block," the case the task asked me to construct). The full 41-test suite, including both new drift tests, **still passes unchanged** against this mutant. Root cause: `drift_block_appends_after_the_composed_prefix_without_moving_it_and_vanishes_when_none` uses the `frame()` helper, whose `telemetry` field is always `""`; since `record`/`notice`/`telemetry` are all empty in every drift test, `with.starts_with(&without)` holds trivially for *any* placement of the drift append among those blocks — the property is exercised only against the (always-empty) base template, never against a populated block that could actually precede or follow it. The claim "proved by `drift_block_appends_after_the_composed_prefix_without_moving_it_and_vanishes_when_none`" in acceptance box 1 is true for "renders after the template" and false for "never... above another tail block" — that half is asserted in prose only. Fix: add one case to the test (or a second test) where `telemetry` is non-empty alongside `drift`, and assert the telemetry block precedes the drift block in the composed output.

**F1 (moderate, task point 5) — the Verify block's timing claim for `just test harness` is not the command it was measured against.**
The spec's Verify-and-Proof comment reports `cargo test -p harness --lib` at 13.97s and states "`just test harness` runs the lib tests plus the four integration binaries... both fit well inside the 120s per-block limit even cold," but the actual `just test harness` command is `cargo test --manifest-path ... -p harness --all-targets` (`.cartridge/memos/routine/cartridge-development.md` line ~93), not `--lib`. **F2 (minor) — box 4's completeness claim has no test coverage of the wiring, only of the leaf functions.**
No test exercises `Request::frame()` forwarding `self.drift.as_deref()` (step 4) or `resolve()` populating `Request.drift` (step 6); only direct `Frame`/`describe_drift` construction is covered. Acceptance box 4 is correctly scoped as a diff-review fact rather than a runtime one (independently re-verified: `lib.rs:658`, `:723`, `:1339`, `working.rs:106`, `inspection.rs:98` — all five call sites read exactly as the table describes, `injection` is the only bare `Frame`), so this is not a defect in the table itself, just a small, free-to-close coverage gap in the two trivial plumbing lines.

**F3 (minor, task point 2) — `Option<&'a str>` on `Frame` buys nothing at the layer it is introduced.**
The spec's own "What is explicitly not designed around here" section admits `resolve_drift` collapses "verified nothing," "call failed," and "op not implemented" all to `None` before `Frame` ever sees the value. By the time `Frame.drift` is read in `build_system`, `None` and `Some(x)` are exactly the binary "render nothing" / "render this text" distinction that `frame.telemetry.is_empty()` already expresses with `&'a str`/`""`. The stated justification — "`report: null` is a real, distinct state, never an empty string" — is true of the wire, but that distinctness is deliberately erased by `resolve_drift` itself before it reaches `Frame`, so `Frame`'s `Option` carries no information `""` could not, at the cost of diverging from every neighbouring field's convention and adding `.as_deref()` plumbing. Defensible if a future caller needs to distinguish the states again, but as designed it is a wart, not a requirement. Non-blocking.

### Ruling on the five points

1. **PRD hint vs. analyst.** The analyst is right, verified independently at the source: `resolve()` (`lib.rs:966-1015`) builds one `Request` that `on_harness`'s `"inspect" | "context" | "compact"` arm shares (`lib.rs:1668-1672` per the PRD's citation, confirmed at the dispatch site), and `inspection.rs:98` calls `build_system(prompt, request.frame(), ...)` — the real report, not an empty one. Only `injection` (`lib.rs:1339`) builds a bare `Frame` by hand. But the PRD's own text (`prd.md` line ~62) poses this as an open question the spec must resolve by reading the call sites, not as an asserted fact — it never claims inspection.rs passes no drift, it flags the uncertainty and defers correctly. No PRD correction is required; the PRD did its job. This point is settled and not a source of deduction either way.

2. **The `Option` decision.** Not justified as designed — see F3. Both answers were called defensible in the brief, and in isolation `Option<&'a str>` is a reasonable way to represent a distinct wire state; the problem is that `resolve_drift` throws that distinctness away before `Frame` ever needs it, so the `Option` at the `Frame` boundary is decoration, not necessity. Minor deduction, non-blocking.

3. **Prefix-stability property.** Structurally designed correctly (drift genuinely is the last append in the source as written), but the test asserting it is vacuous for the one adjacency that matters, proven by running the constructed mutation myself — see B2. Blocking.

4. **Degradation.** The `resolve_shell`/`resolve_environment` precedent is real (verified at `lib.rs:1063-1069`, `lib.rs:1116-1122`, both `Err` → empty/`Null`). Silently degrading a *failed fetch* to the same `None` as "verified nothing changed" is a real, acknowledged tension the spec does not resolve — the PRD's whole point is safety against stale beliefs, and today (and for the entire life of this row before `@sessions` lands) every request degrades this way, not as a rare failure mode but as the constant, only observable behaviour. Given B1, this is moot in practice: even a successful, populated report degrades to `None` too, for an unrelated reason. Not independently blocking (the design tension is disclosed, not hidden), but compounds with B1 into total non-functionality.

5. **Verify blocks.** Re-ran independently in a throwaway copy outside the repository (`rsync -a --exclude target`, isolated `CARGO_TARGET_DIR`, `env -u CARTRIDGE_YOLO` on every command, cleaned up after): `cargo fmt -p harness -- --check` exit 0 (after one whitespace fix to my own hand-applied patch — the spec's code as written is correctly formatted), `cargo clippy -p harness --all-targets -- -D warnings` exit 0, `cargo test -p harness --lib` exit 0, 41 passed (39 existing + 2 new), matching the analyst's report. `cargo test -p harness --all-targets` (the real underlying `just test harness` command) fails in an isolated throwaway copy for a reason unrelated to this spec (no sibling `cartridge.ctg` release build there) but would run in the live checkout where that sibling already exists — not run against the live checkout per the explicit prohibition on building live targets in a shared session. Box 6 is not provable outside the live checkout as spec'd; that is a property of this repository's test layout, not a defect introduced here. Box 4 is correctly a diff-review fact; a narrower footprint would not convert it into a machine check, because the claim being verified ("each call site got the right treatment") is a semantic judgment about five separate call sites already inside the declared footprint, not a boundary-crossing fact `collect` could police by path.
