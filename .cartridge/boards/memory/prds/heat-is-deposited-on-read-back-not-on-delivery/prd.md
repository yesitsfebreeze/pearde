# Heat is deposited on read-back, not on delivery

## Outcome

`commit_access` in `src/retrieval/piece/src/retrieval_score.rs` deposits heat on every
entity a query delivers. Delivery is the engine's own output, so the bank warms what it
chose to show, whether or not the agent read it. Ten rows delivered and one used still
warm all ten. That is the loop the test-model-thing chat mode had: it trained on its
own generated bytes and degraded its weights from forty bytes of use. Retention should
track use. The surviving explicit by-ID read is the use signal for one projection; observational ASP search and expand remain non-depositing.

Deposit the access heat when a reference is deliberately read back through the surviving explicit by-ID read path. Delivery deposits nothing, or a configured fraction
if the retention probe shows that pure read-back starves rows that are useful but
never re-read. The `tool.memory` `query` path keeps depositing until the agent surface
has a read-back of its own, and says so in its help text.

## Acceptance

- [ ] A query followed by no read leaves every delivered entity's heat unchanged.
- [ ] An explicit by-ID read of one reference deposits `deposit_access` on that entity alone; observational ASP search and expand leave heat unchanged.
- [ ] The retention probe from the linked item is rerun before and after, and the table in `.cartridge/tests/integration/bench/RESULTS.md` records both.
- [ ] `heat.rs`'s module header, README and help describe the surviving explicit by-ID deposit point and the unchanged tool-query carve-out.

## Decision (2026-09-19, coordinator, at publish of spec01)

not need to change.

## Decision (2026-09-19, coordinator, after review round 1 failed at 85)

Round 1 scored 85 of 100 with two blocking findings. Both are upheld, and one
of them is a contradiction of this PRD's own Outcome rather than a defect in
the spec's craft.

**Blocking finding 1 stands, and the PRD wins.** The Outcome says the
`tool.memory` `query` path "keeps depositing until the agent surface has a
read-back of its own, and says so in its help text." The spec's Mechanism item
6 reverses that: `task_commit_access` multiplies by a `0.0` fraction, so that
path now deposits nothing and the model's own surface can never warm the bank.
No Acceptance box covers the question either way, so the reversal would have
landed silently. The revision must honour the Outcome — the carve-out is
deliberate, it is the reason this PRD does not simply switch every deposit to
read-back, and reversing it is a product change that is not this PRD's to make.
If the analyst believes the carve-out is wrong, that is a `## Questions`
section for the user, not a quiet inversion inside a mechanism list. Whichever
way it goes, an Acceptance box must pin it, because a behaviour nobody asserts
is a behaviour the next change will flip again.

**Blocking finding 2 is granted as a footprint widening.** `.cartridge/help.md`
is added, making fourteen paths. Its lines 7-9 carry the same `context.memory`
sentence the spec rewrites in `README.md`, it is hand-maintained, and it is the
literal "help text" the Outcome names. The doc gate never inspects it, so the
divergence would have collected green. A cartridge's README and its help page
change together; that is a standing rule here and this PRD was about to break
it.

**The reviewer's work is recorded because it was unusually thorough and should
not be repeated.** All three mutants reproduced exactly as claimed, in its own
clone, with quoted red assertions and exit 101 each. All six `pass:` names were
confirmed as executed `... ok` lines with exact counts. `memory.ctg` declares no
`yolo` setting and has zero `CARTRIDGE_YOLO` references, and gate and mutants
were byte-identical plain and under `env -u` — so no false pass from that
direction.

**The rpc filter is legitimate, for a broader reason than the spec gave.**
Unfiltered `cargo test -p rpc --lib` is green 5 of 5 at `110 passed` on the
patched tree, including the readiness test, so the filter hides nothing this
change breaks. The two-crate command flaked 1-in-4 on the patched tree and
1-in-6 **at base**, on three different tests across runs. The rpc crate has
load-sensitive timing tests unrelated to this PRD. The revision should say that
instead of the narrower story about one test.

**Four non-blocking findings the revision should also fix**, because two of
them are the kind that make a gate ornamental: `a_replayed_read_cannot_pump_one_references_heat`
is vacuously satisfiable — it stayed green under mutant 2 because it never
asserts the captured value is non-zero; box 3's `RESULTS.md` gate accepts any
edit at all, including a literal `# PLACEHOLDER` line; `query_by_ids` changed
but is untested; and the stated timings are about 2.5× optimistic (45 s and
14 s observed cold, still inside the 120-second limit, but the margin claimed
was not the margin measured).
