## Contract and ordered implementation

1. Add failing behavioral tests beside `streams_replay_and_then_deliver_live` in the existing host test module. Reuse local transport server helpers or the host replacement fixture; all servers, sockets and tasks must be stopped or awaited. Observe envelopes through a real RPC peer or subscriber callback, not private channel state. First reproduce both a truncated replay and a fresh publisher receiving an old cursor.
2. Give each publisher generation an opaque random epoch using the existing transport token helper. Add the epoch to channel envelopes and subscribe replies. Resume requests carry `since` plus optional `epoch`. Keep sequence numbers local to a generation. A typed public `StreamCursor { epoch, seq }` and additive `Ctx::subscribe_from` accept a complete saved cursor. Preserve the existing `Ctx::subscribe(..., Option<u64>, ...)` interface as the supported numeric current-generation API, and delegate both paths to one subscription implementation. Numeric-only cursors cannot distinguish generations; document this limitation instead of claiming otherwise. Existing Lua subscriptions need no new arguments: the SDK watcher remembers the epoch for automatic reconnect.
3. For a matching generation (or a legacy numeric current-generation request), if `since + 1` precedes the oldest retained sequence, send exactly one subscriber-local envelope before replay: `kind: gap`, `channel`, current `epoch`, `seq` equal to the last missing sequence, and `data: { reason: "retention", from: <first missing>, to: <last missing> }`. The range is inclusive. Use checked comparisons that cannot overflow at `u64::MAX`. Do not broadcast this gap, store it in history or increment the publisher sequence for it. A fresh subscription without a cursor and an in-range cursor receive no retention gap.
4. On a supplied epoch mismatch, send one subscriber-local `kind: gap` with current epoch, `seq: 0` and `data: { reason: "restart", previous_epoch: <old epoch> }`, then all retained current-generation envelopes in order. Do not invent a missing numeric range across generations. This works when the new generation's sequence is below, equal to or above the old sequence and when the new generation is initially empty. No previous-generation envelopes can be recovered from memory after restart.
5. Make the watcher cursor a synchronized epoch/sequence pair representing a **contiguous accepted prefix**, not a maximum observed sequence. A successfully queued retention gap advances over exactly its declared missing range; a successfully queued restart gap resets the epoch before current-generation data. Advance for ordinary envelopes only after enqueue succeeds. On the first `Full` error, close the Peer, stop the entire connection's receive pump immediately, and drop its incoming receiver and all buffered messages before opening a replacement connection. Do not continue forwarding for another channel on that old Peer after the failure. Freeze each watcher at its last accepted prefix, and reconnect every watcher on that Peer with its own pair. Preserve already accepted callback-queue contents; recovery appends missing envelopes after them. Thus a draining callback cannot let N+1 jump over an enqueue failure at N. A `Closed` callback queue removes that watcher instead of advancing its cursor. Late subscribe replies from a retired connection cannot mutate any cursor. Seed a reply cursor only for an initial no-cursor attachment whose baseline has not already been established by an envelope; replay replies never skip queued data. If recovery again finds a full callback queue, repeat the same stop-and-prefix rule with bounded retry backoff, not a spin loop. Independent subscribers on other Peers continue normally.
6. Implement the bounded admission and ordering mechanism below. Delete the old `QUEUE - 3` retention proposal: keep the existing 1024-envelope retention bound. Publisher code never awaits socket capacity, and failed replay admission never invents a retention gap.
7. Update transport.txt, README.md and .cartridge/help.md in the same implementation with the epoch/cursor contract, inclusive gap fields, legacy numeric semantics, restart recovery limit and bounded nonblocking behavior. Remove superseded claims that a bare numeric cursor alone guarantees restart-safe replay.

## Bounded replay and shared-Peer mechanism

**RPC ownership.** In `rpc.rs`, retain the existing bounded ordinary outgoing queue and its synchronous saturation policy. Add one separate bounded stream-frame queue of capacity `rpc::QUEUE` per Peer. Only the subscription protocol (pumps and ordered teardown controls) uses it. The existing writer owns both receivers and drains them fairly (alternation when both are ready, with either ready queue progressing when the other is empty). It still writes one frame at a time. This isolates ordinary replies/control capacity from replay, rather than claiming unused slots in a shared queue. Add crate-local async notification and reply methods that await a permit on this stream queue, selecting against Peer closure, subscription cancellation and a finite no-progress timeout based on the Ctx connection timeout. Taking a permit is actual admission; a full stream queue yields instead of closing a healthy Peer. A cancelled reply consumes/disarms its `Request` so Drop cannot emit a second ordinary error reply. Timeout or closed downstream aborts the connection. Do not spawn a task per frame, collect waiting frames in an unbounded vector, enlarge fixed spare constants, or route ordinary unrelated replies into a replay buffer. Connection shutdown cancels waiting admission; writer shutdown must complete within the existing bounded shutdown budget, and `flushed` must resolve after writer exit.

**Atomic history-to-live handoff.** Each channel subscriber entry holds a bounded live-tail sender, its cancellation handle and Peer, instead of publishing directly into the RPC queue. Under the channel mutex, a join captures at most HISTORY retained envelopes and its gap decision, allocates and registers that subscriber's tail, and creates the real sequenced `subscribe` control envelope in the same ordered critical section. Send that control to existing subscribers, append it to the new subscription's captured startup sequence, and retain it in channel history as usual. This is a snapshot boundary: every later publish goes into the new tail and has a greater sequence. Capture the reply head at the defined pre-subscribe boundary as before. Keep existing trace hooks when integrating, but the HEAD implementation uses only committed facilities. Share a locked publication helper to avoid recursive locking and competing sequence allocation. No channel mutex is held across an await.

**Pump ownership and memory bound.** One task per active subscription first sends its local gap, the captured replay, the captured subscribe control, and its successful RPC reply through the same stream queue in that order. It then drains its bounded tail through that queue. The connection handler admits only one startup snapshot at a time: await this pump's startup-result signal before handling the next subscribe request. Previously started pumps keep draining their live tails. Host stop and Peer closure interrupt that startup wait. A queued unsubscribe request is processed after startup completes or reaches its finite failure deadline; do not claim that the serial request loop can process it while blocked on startup. Distinct channels may interleave; each channel's replay precedes its live data, and its subscribe reply cannot overtake its replay. A request queued for a second full channel yields on real capacity; it is not dropped just because the first replay is still buffered. Already queued ordinary replies/live frames are finite occupancy, not an assumed empty queue.

The startup vector is bounded by HISTORY plus at most a local gap and subscribe control. Each subscription tail has capacity QUEUE and at most one frame being admitted. Each Peer has two outgoing queues of QUEUE frames and one frame in the writer. The number of long-lived pumps follows the existing subscription set, not event count; only one startup vector is live per Peer. There is no growing replay backlog. These are frame-count bounds, matching the existing frame-size contract; this change does not claim a new byte bound.

**Nonblocking publication and cancellation.** `publish_kind` only updates bounded history and `try_send`s to each subscriber tail under the short channel lock. Tail saturation removes that subscriber and closes its Peer immediately, so all streams on that Peer reconnect consistently. It never waits for the pump, writer, callback or reply. The tail counts live data arriving while replay is in progress; if that bounded tail really fills, disconnect is allowed and recovery resumes from the accepted prefix. An unrelated Peer is unaffected. A startup/admission failure removes the subscriber and reports failure once. Unsubscribe, duplicate same-channel subscribe, client disconnect and host stop cancel the old pump, remove its entry and await/reap its task. Do not retain detached pumps after the connection ends. Cancellation prevents further admissions; already admitted frames may arrive, so same-connection re-subscription must drain the old subscription through an ordered stream barrier before admitting the replacement snapshot, or close/reconnect that Peer. Choose the barrier path for normal unsubscribe/resubscribe so unrelated streams remain usable. A barrier is a bounded queue item acknowledged by the writer after all preceding stream items, not a sleep. Its guarantee is wire ordering, not that the remote callback has drained. The SDK must also order local watcher replacement against its receive pump: retain a tombstone for a removed watcher until a stream-order fence notification sent before the unsubscribe reply has been consumed by that pump. Await that local fence before installing a replacement watcher; RPC reply arrival alone is insufficient because replies bypass the notification receiver. The fence is internal control, not callback data or channel history; enqueue it and the unsubscribe reply, in that order, through the same bounded stream queue. On disconnect, dropping the old incoming receiver satisfies the fence by preventing old-connection delivery. Add this receive-pump fence case to the cancellation regression.

**Deterministic test seams.** Use a gated `typed::Adapter`/writer and explicit notifications or barriers to control frame admission and callback release. A crate-local generic connection entry or narrowly scoped `cfg(test)` wrapper may expose the exact production connection/pump path to the existing host test module; do not duplicate transport behavior in the fixture. For the enqueue-hole race, a test-only observation barrier immediately after the first failed watcher enqueue may pause teardown while the callback releases capacity and later incoming frames are already buffered. The seam must not change queue capacity, sequence values, cursor updates or failure decisions. The test must fail against the old continue-after-close behavior and pass only when later old-connection messages are discarded.
