The first pass scored the tools as they are. The second pass asks a different
question: **is every capability of every tool reachable by the agent at the
moment it applies?** A tool that is written well and never suggested is a
tool scored 79 on the docs site and 0 in the loop.

The thesis is one loop, pointed at ourselves. Scout runs it against GitHub —
discover, ask, curate, wire. The same loop, aimed inward:

| step | scout's version | ours |
|---|---|---|
| index | `buckets.txt` — what is out there | one capability registry — every verb of every tool, generated, doctor-checked |
| suggest | a sweep's ranked rows | the loop injects the rows whose reads and writes meet the pass's footprint — at the brief, at session start, never a wall of tools |
| use | a route call | the suggestion is taken or ignored — either way it is **counted** (the guard already counts calls; this makes the count per capability) |
| rank | `delta` over star snapshots | `delta` over usage snapshots — one TSV per day, the same pattern, the same pruning |

Every page below is atomic: one change, one verifiable done, one named
failure. Together they make "every tool used to its best capability" a
*measured* state instead of an intention — an unused capability is a row
with a delta of zero, named on a page, the way an unhealthy file is named in
the brief today.

## What this pass is not

Not a router, not a model choosing tools, not telemetry for its own sake.
The registry is data the existing readers read; the suggestion is a section
the brief already has (the health pointer, the workflow route); the ranking
is the scout pattern, already proven on external repos. Three mechanisms,
each one reader of one format — the integration axis applied to the
integration layer itself.
