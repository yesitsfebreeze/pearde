View score: **55** — the second worst tool. Root strength: the view renders
board files and writes nothing but board-shaped writes (`state:` through a
drag), so it cannot fork the board.

| axis | score | what pulls it up | what pulls it down |
|---|---|---|---|
| usability | 6 | one command ever (`pearde view`); the URL names the view; fold-by-choice on the three archives | eight sections on one page is a 7065px page before folding; the write affordances (drag, ＋, answer box) are discoverable only by hover |
| integration | 5 | one payload, one service, doctor's `view` row reads registration back | the daemon is state outside the board — a port, a pid, a process table sweep (`reap`) with a grace window; three ways to be broken and only one to be told |
| sensibility | 5 | the read-only `all` page is a clean refusal written in status codes | seven sections plus `all`'s eighth is one concept too many; the fold rules live in prose, not in the renderer's contract |
| complexity | 5 | the tree splits by view section; lit is the one runtime dep | serve, plan, render, mapfile, all, edit and the adapters must agree on the payload; two shipped JS test rigs ride along |
| reliability | 6 | the daemon self-terminates; reap keeps anything watching a live board | the ensure→bind→register window is indistinguishable from a leak — every safety rule since is the debt of that window |
| performance | 7 | swap-in-place keeps scroll and half-typed text; payloads per board, not per request | `/board/all` rebuilds every board's render per request — bounded today, the first wall tomorrow |

**Improve in this order:** integration (move the daemon's liveness into the
board's own directory, where doctor already looks), sensibility (one section
registry instead of eight implicit ones), usability (make the write
affordances visible on focus, not hover).
