# graphify output paths: GRAPHIFY_OUT governs everything, but extract never writes the Obsidian vault

Findings from reading the installed graphify source (uv tool `graphifyy`,
python3.13 site-packages) while relocating this repo's graph output.

**`GRAPHIFY_OUT` is a real, supported override.** `paths.py` reads
`GRAPHIFY_OUT = os.environ.get("GRAPHIFY_OUT", "graphify-out")` at import
time and documents the absolute-path form ("worktrees or shared-output
setups"). `out_path()` and `default_graph_json()` build on it, so `extract`,
`update`, every read command (`query`, `path`, `explain`, `god-nodes`) and
the Obsidian exporter all resolve to the same directory with no flag. Because
it is read at import, it must be set before the process starts.

This contradicts a widely repeated claim (it was written into this project's
own PRD) that extract/update have no output flag and no env var and always
write `graphify-out/` relative to cwd. False for this version.

**`graphify extract` does NOT write an Obsidian vault.** The extract block
(`cli.py:3138-4513`) contains zero occurrences of `obsidian`. The vault comes
only from the separate `graphify export obsidian` subcommand (`cli.py:2996`),
whose output dir is `Path(_GRAPHIFY_OUT) / "obsidian"` (`cli.py:2793`). Any
pipeline that expects a vault after extract needs an explicit export step.

**`graphify update` does NOT write the `.graphify_root` marker.** It only
reads it (`cli.py:2409`) to recover a scan root when no path argument is
given. The marker is written in exactly two places, `cli.py:4270` and
`cli.py:4439`, both on the extract path, both as
`str(Path(target).resolve())` — so it is always absolute and resolved.
Claims that `update` stamps an unresolved relative marker do not match the
code.

**Why the marker matters:** `build.py` prefers it as the authoritative repo
root and otherwise falls back to a grandparent heuristic
(`<root>/graphify-out/graph.json` -> `<root>`), which is wrong for any custom
output dir; the pruning of deleted files is what suffers.
