# std::sync::RwLock is not re-entrant: a second write() on the holding thread deadlocks the test binary rather than panicking, and libtest names no test for a hang

std::sync::RwLock has no re-entrancy. The std docs say a second write() from the thread already holding the lock "might panic"; otherwise it deadlocks, and which one you get is per-platform. On macOS/aarch64 it deadlocked silently.

For a test guard this is the difference between a red and a hang. env_guard_test.rs as first written took an outer env_guard(), then took a second one inside std::panic::catch_unwind to prove restore-on-panic. Under a 45s timeout the binary reported 2 of 3 tests and then stopped: libtest prints nothing for a test that never returns, so the run names no culprit at all — the hang has to be found by reading the lock, not the output.

The consequence for any save-and-restore guard: the state a restore is measured against cannot be established by an enclosing guard of the same type, because the enclosing guard undoes that setup on its own drop and cannot be held while the inner one is taken. Establish it inside the single guard under test (a variable the test added), or read it off a variable the process already had (PATH), and make the post-drop assertion under the read half of the lock.
