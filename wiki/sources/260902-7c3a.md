# .chezmoiremove removes a deployed orphan, but only while chezmoi still recognises the file it wrote

`chezmoi apply` will not delete a target whose source file was deleted
(already on record as [[260902-f203]]). The repo-carried remedy is
`home/.chezmoiremove`: one target path per line, relative to `$HOME`, no
leading dot-slash. Measured 2026-09-02 in this repo.

Two shapes, and only one of them is quiet:

- The target is byte-identical to what chezmoi last wrote, and chezmoi's
  state still knows the entry. A **scoped** `chezmoi apply ~/.config/nushell`
  removes it silently, exit 0. Proven by planting `git show
  HEAD:home/dot_config/nushell/copymode.nu` (307 bytes) at
  `~/.config/nushell/copymode.nu`, applying scoped, and finding it gone.
- The target differs from what chezmoi last wrote — or chezmoi has already
  forgotten the entry, which is what happens on the *second* plant after a
  successful removal. Then chezmoi asks
  `.config/nushell/copymode.nu has changed since chezmoi last wrote it?`
  and in a session with no controlling terminal that is not a skip: it is
  `chezmoi: … could not open a new TTY: open /dev/tty: device not
  configured` and **exit 1 for the whole apply**. `--force` answers it and
  removes the file.

The consequence for any automated deploy or verify script: a
`.chezmoiremove` line can turn a green headless apply red on a machine
where the user had edited the file being retired. Either apply `--force`
where the retirement is intended, or assert the target's absence rather
than assuming the apply handled it.

The scoped form does process removals — `.chezmoiremove` is not skipped
just because the apply names paths rather than running bare.
