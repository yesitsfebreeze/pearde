# A rebound module global cannot travel by from-import when a module is split

Splitting a Python module moves names into new files, and `from newmod import
name` in the old one makes every one of them reachable again — except a global
the code rebinds at run time.

`plan.py` held three: `_PCACHE`, `_PCACHE_LOADED` and `_PCACHE_DIRTY`, the
parse cache and its two flags. `parse_cache_load` declares `global _PCACHE,
_PCACHE_LOADED` and assigns them; `parse_prd` assigns `_PCACHE_DIRTY`. A
`from prdfile import _PCACHE_DIRTY` in the module that reads it binds the value
it had at import time and never sees another. The reader has to go through the
module — `prdfile._PCACHE_DIRTY` — and so does anything outside that writes one:
a test that did `planlib._PCACHE_LOADED = True` sets an attribute on `plan` that
nothing reads, and fails silently rather than loudly.

Two consequences worth carrying:

- When a split has to keep an old module importable as a facade, the rebound
  globals are the names that cannot be re-exported. Everything else can.
- A harness that pokes a module global from outside is pinned to which file
  holds it. It is the one kind of caller a split cannot leave unchanged, and
  the cheapest fix is to address the owning module by name.
