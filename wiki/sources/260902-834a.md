# A sync closure over reqwest::blocking panics on an async caller, and block_in_place is not the fix

`reqwest::blocking::Client` carries a runtime of its own, and dropping one
inside an async context panics: `Cannot drop a runtime in a context where
blocking is not allowed`. So a SYNC closure that builds a blocking client
inside itself panics whenever an async consumer calls it straight off a task —
which is exactly the shape of a sync-closure contract handed to an async
engine.

Four placements, measured, on the same closure:

| placement | before | after |
|---|---|---|
| bare call from an async task | PANICKED | returns |
| inside `tokio::task::block_in_place` | returns | returns |
| inside `tokio::task::spawn_blocking` | returns | returns |
| bare call on a current-thread runtime | PANICKED | returns |

The obvious fix — `block_in_place` inside the closure — is wrong: it panics on
a current-thread runtime with `can call blocking only when running on the
multi-threaded runtime`, verified as a control in the same run. A library
handing a closure to an unknown consumer does not choose the consumer's
runtime flavour, so it cannot use it.

What works on both flavours: check `tokio::runtime::Handle::try_current()`,
and when a runtime is present run the blocking call on a `std::thread::scope`
thread and join it. Outside a runtime, call straight through and spawn
nothing. Re-raise a caught panic with `resume_unwind` rather than swallowing
it, so a transport bug does not arrive disguised as an outage.
