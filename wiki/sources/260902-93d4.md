# Concurrent cargo tests that spawn subprocesses inherit each other's listening sockets on macOS

Measured, not read: three tests in one cargo test binary, each binding a
TcpListener and handing it to a `/bin/sh` child, failed roughly half of runs
with `Address already in use (os error 48)` on a port whose only holder had
provably been killed and reaped. Serialising the tests with a single
`static SPAWN: Mutex<()>` made it green on every run; nothing about the code
under test changed.

The mechanism is fd inheritance across a concurrent fork. Between
`TcpListener::bind` and `Command::spawn`, the test process holds the listening
socket. A `Command::spawn` issued by another test on another thread forks in
that window, and the fork copies the socket into a child that then outlives the
unload the first test is measuring. macOS has no atomic `SOCK_CLOEXEC` flag on
`socket(2)` the way Linux does, so Rust's std sets close-on-exec in a second
syscall (`ioctl(FIOCLEX)`) and there is a real window between the two to lose.

Consequence for anyone writing a test that both holds a socket and spawns a
process: the fix is to serialise the whole test body, not to add a retry loop
around the assertion — a retry converts a real leak into a slow pass. The
guard has to cover bind-to-spawn for every test in the binary, because the
racing fork is the sibling's, not your own.
