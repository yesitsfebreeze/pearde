# Sourced practitioners behind the mentor persona, and the one behaviour research could not back

Six practitioners, each verified against a real artefact, back one behaviour of
`@references/personas/mentor.md`.

| practitioner | trait taken | source |
|---|---|---|
| Peter Naur | hold the theory that explains why the code is built this way | "Programming as Theory Building" (1985), *Microprocessing and Microprogramming* 15(5) |
| Sandi Metz | name what duplication costs before naming what the abstraction costs | "The Wrong Abstraction" (2016), sandimetz.com |
| Greg Wilson | state the general principle, then give the concrete example | *Teaching Tech Together* (2019), §5.1 "Six Strategies" |
| Andy Hunt | give a novice rules and an expert latitude | *Pragmatic Thinking and Learning* (2008), ch. 2 |
| Tanya Reilly | better wrong than vague — commit to a recommendation | *The Staff Engineer's Path* (2022), ch. 5, on writing an RFC |
| Camille Fournier | mentor through the real project's milestones, not separate lessons | *The Manager's Path* (2017), ch. 2 "Mentoring" |

The three-answers-with-a-recommendation shape is **not** a practitioner stance.
Reilly, Will Larson's *An Elegant Puzzle*, Michael Nygard's ADR format and
Fournier's decision writing were all checked; each documents committing to a
recommendation, none documents the count of three. The count is this board's
own format in `@references/drill.md`, so the mentor's bullet traces to Reilly
for the recommendation and cites nobody for the three — a persona bullet may
carry the board's contract, but it may not attribute it to a practitioner.
