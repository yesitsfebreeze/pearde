# An adapter launch is not a live worker: two tests separate them

A dispatcher that counts `subprocess.Popen` returning has counted a worker that
may never exist. Measured with a stand-in adapter binary that prints
`API Error: 402 {"error":"credit balance"}` and exits 1: the Popen call
succeeds, the pid is real, and `proc.poll()` is `None` for the first few
milliseconds — so "it started" is never the test. Two tests together separate a
launch from a worker, and neither is sufficient alone:

1. **A launch grace window.** A process that has exited 0 in under ~2 s did
   not work anything; a real pass session is minutes. A worker that dies at
   second 30 passes this test at second 2, so it is only ever consulted on a
   process that has already exited.
2. **A scan of the run log** for `API Error`, `credit balance`, `402`, `429`,
   `rate limit`. This is what @references/agents/pearde-pass.md already tells
   the pass worker to do to its own subagents ("its transcript file must exist
   and hold no `API Error`"), applied one level up. It is only consulted on an
   exited process: a 429 that was retried and recovered appears in the log of a
   perfectly live worker.

The consequence for concurrency: the load meter
(`resources/board/machine.py`, and [[260902-5c4d]]) is a proxy for a bound it
cannot read. What actually bounds this machine is the model gateway, and it
surfaces as a dead worker rather than as load. So a slot is freed by the
liveness test, not by the meter, and a dead worker is re-dispatched once before
it is named.
