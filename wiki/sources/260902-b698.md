# kern 2.0.0 creates an empty store when it finds none, so a missing store reads as dead ids

`kern` v2.0.0 resolves its store from the working directory. When it finds no
`.kern/data` there, it **creates an empty one** and answers `kern get: no
thought with id <id>` for every id asked of it. That answer is byte-identical
to the answer for an id that genuinely does not exist, so a store that is
merely in another directory is indistinguishable from a store that is gone.

Reproduced in a clean temp directory on 2026-09-02: `kern get 629fc82759c9`
printed "no thought with id" and left a new `.kern/data/{data.mdb,lock.mdb}`
behind. The same call under `KERN_DIR=<the real store>` resolved the id.

This cost a real wrong conclusion in `shared`: on 2026-08-28 an index of 21 ids
(`.pi/ontology/digest.md`) was measured from the repository root, every id came
back "no thought with id", and the whole index was recorded as dangling and its
store as "neither present nor recoverable". The store was present the whole
time at `.pi/kern`, and all 21 ids resolve under `KERN_DIR`.

The grep for plaintext that seemed to confirm it is a second false negative:
`kern` stores thoughts encoded in LMDB, so `strings data.mdb | grep <term>`
returns 0 hits for terms that are demonstrably in the store.

Consequence for any check over a kern store: resolve and test the store
directory **before** invoking `kern`, and report an absent store as unknown
rather than as dead ids. `kern status` prints the resolved data dir and every
other store on the machine, and `KERN_DIR` pins it.
