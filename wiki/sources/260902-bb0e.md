# Concurrent cargo test invocations serialise on the target-directory lock, so an N-way load measurement has to run the built test binary directly

Measuring what a timed test actually waits under load means running several
copies at once. Doing that with `cargo test` measures nothing: cargo takes an
exclusive advisory lock on the target directory for the build phase, so the
second and later invocations block ("Blocking waiting for file lock on build
directory") and the tests end up running one at a time on an otherwise idle
box.

The fix is to build once with `cargo test --no-run --message-format=json`,
read the `executable` field off the artifact message whose `profile.test` is
true, and run that binary directly N times in parallel. Observed in the kern
tree: the same three tests measured 205ms / 21ms / 1.4ms median alone and
206ms / 21ms / 1.3ms four-way — the tails moved (shutdown max 4.5ms to 7.2ms)
and the medians did not, which is only readable because the copies were
genuinely concurrent.
