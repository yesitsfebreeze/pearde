# git stash push -u removes a directory it empties, and takes the process cwd with it

`git stash push -u -- <pathspec>` stashes untracked files and then REMOVES
the directory whose last entry it took. `git stash pop` recreates the path,
but as a new inode.

A process standing in that directory keeps the deleted one. From that point
`os.getcwd()`, `os.path.abspath()` and every relative `open()` raise
`FileNotFoundError`/`OSError(ENOENT)` for the rest of the run — the path
exists on disk and is still unreachable through the process's own handle.

Measured: `collect.py`'s verify guard parks foreign dirt with
`git stash push -u`. Run as `collect --also <relative path>` from a
subdirectory of the checkout, the park emptied and removed that
subdirectory, and `also_places`'s `os.path.abspath(a)` then died with
`FileNotFoundError` — a green verify block, a traceback, nothing committed.
Seven checks in `filing-refuses-a-file-it-does-not-hold`'s harness went red
on it (52/52 -> 45/52) and nothing in the guard's own probe saw it.

The repair is not to avoid the stash: capture `os.getcwd()` before the park
and `os.chdir()` back to it after the pop when `os.getcwd()` raises. A
chdir to the same absolute path attaches to the recreated inode.

The general shape: any tool that stashes, cleans or otherwise removes
directories under a caller must treat the caller's cwd as state it has to
put back, exactly like a branch or a file.
