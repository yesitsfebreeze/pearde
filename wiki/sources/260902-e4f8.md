# A .chezmoiignore gate keeps a file off future machines but never retires the copy already deployed

`.chezmoiignore` is always evaluated as a template, so an opt-in gate on a
marker file works: `{{ if not (stat (joinPath .chezmoi.destDir ".flag")) }}`
around the target paths. Measured in an isolated source/dest pair, five legs:

- no marker: `chezmoi ignored` lists the path, apply does not deploy it, and
  unignored siblings land normally.
- marker present: apply deploys it.
- **marker removed again: the deployed copy stays.** Ignoring a path is not
  retiring it — the gate only governs machines that have not had the file yet.
  A "make it opt-in" change therefore buys nothing on the machine that already
  carries the file; that machine still needs a `home/.chezmoiremove` entry.
- source file deleted outright: the deployed copy still stays (the same shape
  the record already holds for deletions).
- `.chezmoiremove` naming the target path: gone from the machine.

Use `.chezmoi.destDir`, not `.chezmoi.homeDir`, in a gate you want to be
testable: `homeDir` resolves to the real user's home even under
`--destination`, so a marker planted in a fixture is never seen and the gate
reads as permanently closed. In production the two are the same directory.
