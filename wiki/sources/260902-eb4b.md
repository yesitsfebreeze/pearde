# A nushell def sourced from config shadows an identically-named binary on PATH

`which <name>` in nushell answers the *.nu file that defines `<name>`, not the
executable on PATH, whenever a sourced module carries `def <name>`. The custom
command wins; the binary is unreachable by that name until the `source` line
goes.

Measured 2026-09-02. `~/.config/nushell/litellm.nu` defines
`def --wrapped cll [...]` and is sourced from `config.nu:236`. With
`~/.local/bin/cll` present and first on PATH:

    nu -l -c 'which cll | get path | first'
    # -> /Users/feb/.config/nushell/litellm.nu

Deploying a config.nu without that `source` line into a throwaway destination
and pointing nu at it flipped the same command to `/Users/feb/.local/bin/cll`,
with nothing else changed — so the `source` line is the whole cause.

Why it matters: a spec that proves "the binary moved" with `nu -l -c 'which X'`
is not testing PATH at all while any sourced module still defines `X`. The
check passes or fails on the shell config, not on the install. Retire the
module first, or assert with `command -v X` in a POSIX shell.
