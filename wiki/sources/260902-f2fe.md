# Rebase then ff-only is how a lane lands as one commit; a plain merge writes two

Measured in a fixture repo on 2026-09-02 while probing every-worker-runs-in-its-own-worktree.

A plain `git merge lane/<slug>` onto a checkout that has moved since the lane was cut writes a merge commit on top of the lane's own commit — two commits for one PRD:

    *   d9c61b5 Merge branch 'lane/p2'
    |\
    | * bda49b4 p2 — probe
    * | 6c06e01 main moves on

pearde's invariant is one commit per PRD on the transition that lands it (@references/parts/commits.md), so a plain merge breaks it whenever anything landed while the worker ran — which on a board assuming unlimited agents is the common case, not the edge.

`git merge --squash` gives one commit but the lane branch never reads as merged, so `plan.lanes` would draw every landed lane as work still in flight forever.

What measured clean: rebase the lane onto the checkout's branch, then `git merge --ff-only`. The result was linear, one commit, and `git branch --merged main` listed the lane. A rebase conflict surfaces the same way a merge conflict does.

Also measured: `git merge` of a conflicting lane, then `git merge --abort`, leaves the checkout exactly where it was and the lane branch holding the worker's commits — so a red collect can name the conflicting file and lose nothing.
