# a staged deletion is still an unmatchable pathspec

Measured on pearde, 2026-09-03, git 2.55.0 (macOS):

`git add -A -- <path>` fails with `fatal: pathspec '<path>' did not match
any files` not only when the deletion is COMMITTED — it fails just the
same when the deletion is only STAGED (porcelain `D ` in column 1, e.g.
via `git rm`). Pathspec matching walks the index and the worktree; a path
gone from both matches nothing whatever flag precedes `--`. Measured in
three shapes: staged-by-`git add`, staged-by-`git rm`, and a lane's real
standing dirt (the `the-template-twins-fold-into-the-reference` lane holds
its seven `.doc.md` deletions staged, uncommitted).

Consequence for the collect fix ("stage what stands, not the union"):
`standing` = `git status --porcelain` paths, which INCLUDES staged
deletions. A lane that staged its deletions puts those paths in the
standing intersection, and `git add -A -- *mine` aborts whole on them —
the exact abort the fix removes for committed deletions, one shape later.
The standing set that stages cleanly is the paths still in the lane's
index or worktree: a staged-deletion path needs NO staging (the lane's
next commit or the merge carries the removal), same as a committed one.
`git ls-files -- <path>` per path, or porcelain column 1 != `D`, separates
the two.
