# A vendored crate rename writes two directories, not the vendor root

A crate rename inside a vendored tree writes only the two version directories,
never the vendor root. Measured in mitosys 2026-09-03: `vendor/` holds 25254
tracked files; the `conserved` -> `shared` rename moved 24 of them, all under
`vendor/conserved-0.1.0/` (gone) and `vendor/shared-0.1.0/` (new). No other
vendored crate's bytes moved, even though `just vendor` does `rm -rf vendor`
and stages a fresh tree in whole.

So a PRD footprint spelling `vendor/` over-claims by three orders of magnitude,
and `pearde collect`'s contention check serialises every PRD touching the code
repo behind it. The honest spelling is the two version directories. The caveat
that keeps it honest: `just vendor` regenerates the whole directory, so a change
that also moves a dependency version writes more, and the narrow footprint must
be re-measured per rename rather than assumed.

Note also that [[260902-78b6]] ("mitosys is the one consumer still pinning the
family crate as conserved") is closed by this run: mitosys now pins
`shared` at `dfc98fba70039863797f7185d860ef392becb21f`, the same rev model and
realm pin.
