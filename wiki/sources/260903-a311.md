# still-reachable-leaks-at-exit-are-noise-growth-across-summaries-is-real

Memcheck reports "still-reachable" blocks at process exit from libc/allocator internals by default — these are not bugs, so leak-check verdicts should be read off "definitely lost" and "indirectly lost" only. A single end-of-run report can't distinguish a fixed startup leak from a per-iteration growth, so the diagnostic move for a long-running process is two leak summaries at different points in the same run: send a termination signal (SIGTERM, or SIGINT twice) mid-session to force valgrind to print its current leak state, drive the program between the two summaries, and treat a rising definite-lost count as the real leak signal.
