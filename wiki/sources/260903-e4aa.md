# grep -q under pipefail reddens a match: the early exit SIGPIPEs the writer and the pipeline returns 141

The known pipefail hazard is a false GREEN — `probe | head -1` throwing the
failure line away. The mirror case is a false RED, and it is the one a harness
over a large file walks into.

`set -o pipefail` (no `-e` needed) plus

    tail -n "+$start" "$FILE" | grep -qE "$row"

reports failure for a row that is present. `grep -q` exits at the first match,
`tail` is still writing, `tail` dies on SIGPIPE with 141, and pipefail makes 141
the pipeline's status. Measured on manola 2026-09-03: a harness asserting 32
ledger rows exist printed "no reading on <key>" for all 32 while every row was
in the file and the identical `grep -E` matched when run by hand. The bug is
invisible under `bash -x`, which shows a command line that is correct.

Fixes, in order of laziness:
  `hit=$(… | grep -cE "$row"); [ "$hit" -ge 1 ]` — `grep -c` reads to EOF, so
    no writer is ever signalled.
  drop the pipe: `awk -v s="$start" 'NR>=s && /re/ {f=1} END{exit !f}' "$FILE"`.
  `grep -q` is safe only when nothing feeds it through a pipe.

Same shape, same cause as `head -N` after a producer; the difference is that
`head` loses evidence and `grep -q` invents a failure.
