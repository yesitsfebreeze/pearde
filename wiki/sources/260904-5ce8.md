# A lane's own .pearde symlink makes every drop_lane checkpoint fail on a board whose repo does not gitignore it

Since `lanes.create` gives each lane a `.pearde -> ../..` symlink (commit
3904b7b, "a lane and a session tree can read the board they were cut for"),
that symlink is a path inside the lane worktree. `lanes.dirty` reads
`git status --porcelain` in the lane, so on a repo whose `.gitignore` does
not name the board the symlink comes back as `?? .pearde` and the lane is
"dirty" even when the worker left nothing.

`drop_lane` then enters its checkpoint branch and `lanes.commit_all` runs
`git add -A`, which git refuses on that path:

    The following paths and/or pathspecs matched paths that exist
    outside of your sparse-checkout definition, so will not be
    updated in the index:
    .pearde

`commit_all` raises `LaneError`, `drop_lane` prints `<who>: <prd> checkpoint
failed — …` and `lanes.remove --force` then takes the lane with everything
uncommitted in it. On a clean lane that is a false data-loss report; on a
dirty one the checkpoint that exists to save the worker's build does not run
and the build is genuinely gone.

The pearde repo itself gitignores `/.pearde` and `/pearde`, so this is
invisible there. `init.py init` writes no `.gitignore`, so it fires on every
freshly initialised board and in every harness fixture built with
`init.py init` — reproduced in a throwaway repo on 2026-09-04, and it stops
the moment `printf '/.pearde\n/pearde\n' > .gitignore` is committed before
the first `claim`.

Two consequences for a caller: `drop_lane`'s return value is the only signal
that the drop kept the work (it now answers False when paths went
uncommitted), and any edge that deletes `lane/<slug>` after a drop must read
it — the branch is the only place the work is not.
