# lazy.nvim reads a plugin store symlink as not-installed

Seeding a staged `~/.local/share/nvim/lazy` with **symlinks** pointing into a
real store makes lazy.nvim report every seeded plugin `not installed`, even
though the symlink resolves and `ls` inside it lists the plugin's files.
lazy's root scan classifies dirents by type, and a symlink's type is `link`,
not `directory`.

Measured: a headless `HELP_CHECK=1` start over a symlinked store printed
`Plugin claudecode.nvim is not installed` (and the same for tinted-nvim,
persistence.nvim, oil.nvim), `:ClaudeCode` failed with
`Vim:Plugin claudecode.nvim is not installed`, and `require("claudecode")`
fell back to stock defaults — `split_width_percentage=nil`,
`terminal_cmd=nil` — which reads like a config bug rather than a staging bug.
Re-seeding the identical set with `cp -Rc` (APFS clonefile, so still cheap
and near-instant) made all 23 plugins load, `git calls: 0`, and the real
merged config appear.

The trap is that the failure is silent in the shape that matters: the probe
still exits 0 and still prints a plausible config, so a harness that seeds by
symlink measures lazy's defaults and calls them the config under test.
