# claudecode.nvim forces split_side right onto the claude-tmux provider

`claudecode.nvim`'s `terminal.setup()` ends with `get_provider().setup(defaults)`
(`lua/claudecode/terminal.lua:584`), and `defaults.split_side = "right"`
(`terminal.lua:11`). `claude-tmux.nvim`'s provider `setup` force-merges what it
is handed over its own state (`lua/claude-tmux/init.lua:164`,
`vim.tbl_deep_extend("force", state.config or {}, config)`).

So any `split_side` a user passes to `claude-tmux.setup{}` before
`require("claudecode").setup()` is overwritten. There is no way to pass
`"bottom"` through claudecode either: its validator accepts only `"left"` or
`"right"` (`terminal.lua:206` and `terminal.lua:454-458`), warning and
discarding anything else. `split_size` and `toggle_key` survive, because
claudecode's defaults carry no such keys.

Measured twice with different inputs inside a real tmux session (private
socket), firing the real `:ClaudeCode` command: with `split_side = "bottom"`
and again with `split_side = "left"`, `claude-tmux.get_config()` answered
`split_side=right` both times, and the pane tmux created was a 60-column
right split of a 200x50 window (`h=49 w=60` beside `h=49 w=139`), never a
bottom split.

Consequence for a config: calling `claude_tmux.setup{ split_side = ... }`
inside claudecode's `config()` is dead configuration. Re-asserting it *after*
`require("claudecode").setup(opts)` would win, since the provider reads
`state.config.split_side` at open time (`init.lua:201`) — untested here.
